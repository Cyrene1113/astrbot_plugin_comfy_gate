## 1. 版本现状快照（v1.1.0）

单文件插件 [main.py](../main.py)（594 行），对外只暴露一个 LLM 工具 `comfyui_render(prompt, negative, workflow)`：

- **执行链**：秒级校验（私聊管理员闸门 / workflow 解析 / prompt 非空）→ 后台任务全异步（中文翻译 → 探活/拉起 ComfyUI → 复制基准工作流改词 → 自动挂角色 LoRA → 随机 seed → 提交 → 轮询下载 → 静默推图 → LLM 生成衔接语 → 向会话历史注入「图已送达」提示）。
- **权限模型**：群聊全员（走 `tool_permissions` 默认 member）；私聊仅全局管理员，非管理员返回拒绝文案（见议题 D1 的痛点）。
- **外部依赖**：`~/.astrbot/data/skills/comfyui-pipeline/scripts` 的 `comfy_common` / `start_comfyui`（`sys.path` 插入复用）；工作流目录 `F:\ComfyUI-aki\...\workflows`（绝对路径写死）。
- **数据文件**：`data/character_lora_map.json`（角色 → LoRA 映射，外部文件优先、内置表兜底）。
- 相对 2026-10-16 备份的增量：角色 LoRA 自动挂载、LLM 衔接语、上下文注入、工具返回改为中性状态串、别名表更新（风堇替换画风only）。

## 3. 设计讨论

### 议题 D1：私聊环境插件静默化（讨论中，2026-10-24 提出）

#### 1) 背景与痛点

现状：私聊非管理员调用 `comfyui_render` 时返回拒绝文案（main.py:402-403），LLM 会把这段文案转述出来。

痛点：LLM 有时把**与画图无关的私聊内容**误判为生图请求而调用工具，此时拒绝文案反而让 bot「接管对话」，凭空发起一轮拒绝回复——用户没提画图，bot 却说「私聊里出图只对管理员开放哦～」。

#### 1b) 需求澄清（2026-10-24 第二轮，拍板）

「静默」的准确含义是**插件层面失活，不是对话层面失声**：

- 要的是：私聊环境里插件功能**不使用**——不出图、不发消息、不参与对话，LLM 服务照常运行、照常自然回复。
- 明确不要：抑制 LLM 回复。若整轮消息被静默吞掉，用户在不读日志的情况下**无法区分**「消息因延迟/故障没被 bot 收到」和「被误判为生图请求而遭抑制」——这种歧义不可接受。
- 由此**方案 A（stop_event 丢弃整轮）排除**：它恰恰制造上述歧义，且历史留 "Stop output./Output stopped." 工件、丢弃同轮流式内容。
- 验收标准（隐含）：私聊中 bot 对每条消息都有正常的 LLM 回复；插件在其中零可见痕迹（无图、无文案、无状态消息）。误触只允许消耗一次不可见的工具往返，不得改变回复的自然性。

#### 2) 框架机制核查结论（AstrBot v4.28.0-desktop 源码验证）

| # | 结论 | 证据 |
|---|---|---|
| M1 | **框架没有按群聊/私聊场景过滤工具的机制**。工具集只按 persona 配置和 `tool.active` 组装，LLM 在私聊里永远能看到 `comfyui_render` | `F:\AstrBot\backend\app\astrbot\core\astr_main_agent.py:607-620`；全 core 无 MessageType 相关工具过滤 |
| M2 | **WebUI 工具权限是「调用时拦截」而非「隐藏工具」**：无权限时工具仍在 schema 里，调用后由 `_PermissionGuardedTool` 返回一段英文错误文本喂给 LLM——和现在的拒绝文案是同一类污染，只是换成英文，**不能**实现静默 | `core\provider\func_tool_manager.py:463-493, 512` |
| M3 | **工具返回 None/空不能静默**：框架会自动补 "The tool returned no content." 作为工具结果继续喂给 LLM，模型仍会产生一轮回复 | `core\agent\runners\tool_loop_agent_runner.py:1224` |
| M4 | **唯一的硬静默路径是工具内调用 `event.stop_event()`**：agent 循环检测到事件停止后中止本轮，最终 LLM 回复被抑制、不发送。但有副作用：① 会话历史被追加两条固定消息（user "Stop output." / assistant "Output stopped."）并照常落库；② 同一轮已流式输出的文本/并行工具调用会被丢弃或截断；③ 依赖框架内部行为，版本升级需回归验证 | `core\astr_agent_run_util.py:26-27, 157-181`；`tool_loop_agent_runner.py:1494-1528`；历史落库守卫 `core\pipeline\process_stage\method\agent_sub_stages\internal.py:415` |
| M5 | 本部署 `show_tool_use_status=false`（默认值，未开启），工具调用状态消息不会外漏——**硬静默方案在当前部署视觉上是干净的** | `data\cmd_config.json`（`show_tool_call_result: false`）；默认值 `core\config\default.py:134` |
| M6 | persona 支持按工具名白名单（`persona["tools"]`）。理论上可做「群聊 persona（含工具）/私聊 persona（不含工具）」实现 schema 级隔离，但 persona 是按会话人工切换的，没有按场景自动指派机制，运维成本高 | `astr_main_agent.py:613-617` |

**推论**：「工具对私聊不可见」在现有框架上做不到（M1/M2/M6）。「已调用后不出声」只有 M4 一条路（硬）或操控模型输出（软，M3 决定了无法真空）。结合 1b) 的需求澄清——不能抑制 LLM 回复——**M4 这条路也被排除**，只剩「事前少误触 × 误触后软消化」的组合。

补充验证（M7）：理论上还有一条「动态摘工具」路线——在 LLM 阶段之前的消息 handler 里翻转工具对象的 `active` 标志（wrapper 在每次请求组装时镜像该标志，`func_tool_manager.py:243` + `astr_main_agent.py:607` 每请求重建工具集）。但 `active` 是**全局共享对象上的标志**，群聊/私聊消息并发处理时会互相覆盖（私聊刚摘掉、恰好并发的群聊请求组装工具集时功能就没了），且与 WebUI 的启停管理相互干扰。并发脏、依赖内部时序，**记录但不采用**。

#### 3) 方案空间

**方案 A：硬静默（stop_event 丢弃回合）** —— ❌ **已排除（1b) 需求澄清）**
私聊非管理员被调用时 `event.stop_event()`，整轮丢弃。
- 排除理由：抑制的是 LLM 服务而非插件——用户无法区分「消息没送达」与「被静默吞掉」，制造不可接受的歧义；另有历史工件（"Stop output./Output stopped."）、同轮流式内容被丢弃、依赖内部行为等问题。
- 保留记录供回溯，不再进入候选。

**方案 B：软消化（中性空操作 + 自然续接）** ✅ 兜底方向
误触时插件**什么也不做**（不起 ComfyUI、不发消息、无副作用——闸门本来就在流水线之前，只需把返回值改掉），把拒绝文案换成给 LLM 的续接指令，例如：「（出图工具在当前会话不可用，本次未执行任何操作。请忽略这次调用，直接自然回应用户刚才的消息；仅当用户明确要求画图时，才顺口提一句群聊里可以画。）」
- 与「插件失活」的关系：功能层面完全失活，唯一足迹是一次**用户不可见**的工具往返（本部署未开工具状态显示，M5），对外等同于插件不存在。
- 代价：遵从度依赖模型。强模型下回复自然无缝；弱模型可能仍接一句不该接的话。可与极简中性返回值（如「noop」）做 A/B 对比测试，选漏话率低的。

**方案 C：事前防误触（治本，纯 docstring，无代码）** ✅ 主方向
在工具描述里写死场景规则：「私聊场景：除非用户以明确祈使句请求生成图片（如"帮我画/生成一张…"），否则绝不调用；私聊非管理员请求画图时不要调用工具，直接在回复里自然告知群聊可用。」
- 与 B 的分工：C 让「该调用时不调用、该引导时对话层引导」，把误触率压到最低；B 兜住漏网的误触。两者叠加后，私聊里的期望行为 = LLM 正常对话（含画图请求的自然引导），插件零参与。
- 代价：同样是概率性约束；强模型效果好，弱模型仍有漏网。

**方案 D：双 persona 架构隔离（记录备查，不推荐先做）**
群/私聊分别指派含/不含工具的 persona，实现 schema 级不可见（M6）。彻底但要人工维护两个 persona 的同步（人设文案 ×2），且依赖用户在会话里正确切换，自动化需另写插件跟随场景切 persona——成本与收益不成比例。

**方案 E：动态摘工具（记录备查，不采用）**
见推论处 M7：前置 handler 翻转 `tool.active`。全局标志并发脏，群/私聊消息交错时功能随机丢失，弃。

#### 5) 讨论结论（2026-10-24，方向已定，待最终细节确认）

**C + B 组合**为既定方向：

1. **C（docstring 场景规则）为主**：把私聊调用门槛和「画图请求→对话层自然引导去群里」写进工具描述，从源头减少误触。私聊里 LLM 正常对话，插件零参与——这正是「插件在私聊不生效」的可实现形态。
2. **B（中性空操作 + 续接指令）为兜底**：漏网误触发生时，插件不执行任何功能、只返回续接指令，LLM 自然回应用户原消息；bot 每条消息都有回复，不存在「被吞」歧义。
3. 部署现状已核实满足「零可见痕迹」前提：工具状态显示未开启（M5）。
4. A / D / E 均已排除并记录回溯理由。

### 议题 D5：提示词保真度——约束与格式词表（讨论中，2026-10-24 提出）

#### 1) 现象与问题定位：四级损失模型

现象：出图内容与 LLM 给的描述不完全符合，疑似提示词不完善、没被模型完全理解。
但「不符合」不是单一环节的问题——提示词从用户口到成图要过四道手，每道都可能丢信息：

| 层级 | 环节 | 典型损失 | 现状 |
|---|---|---|---|
| L1 | 主 LLM → 工具参数 | 人设 LLM 把用户需求**压缩/转述**，丢细节（背景、服装 specifics、镜头）；把叙述句混进 prompt 参数 | docstring 已引导给英文 tag，但无结构约束、无「不得省略用户细节」指令 |
| L2 | 翻译 → danbooru tag | 译出模型**不认识的词**（描述短语而非 danbooru tag）；角色名被瞎猜成错误角色 tag；质量词被重复输出（工作流本体已带） | `_TRANSLATE_SYSTEM` 是一次性裸调用，无词表、无结构模板、看不到用户原话 |
| L3 | 追加拼接 → CLIP 编码 | **注意力衰减**：工作流基准词在前、用户新词追加在末尾，恰好落在 CLIP 注意力最弱的位置；超 75 token 分块切断 tag；全部等权重，主体词没有强调 | 追加式拼接是既定设计（汐小姐要求：不动工作流原词）；全流程无权重语法 |
| L4 | 模型能力 | checkpoint 本身不认识的概念、多角色构图、手部细节等；以及采样随机性（同一 prompt 本来就会出不同结果） | 不可通过提示词根治，靠重摇（seed 已随机化） |

诊断要点：注入提示里的 `prompt_desc`（main.py 已回显翻译后 tag）就是「实际送进模型的词」——出图不符时先比对「用户原话 → LLM 给的 prompt → prompt_desc 实际值」即可定位损失在哪层，避免盲目堆方案。

#### 2) 方案空间（按层级组织）

**方案 S1（治 L1+L2，纯文案零代码）：统一结构化槽位模板**
把「格式词表」落成一份**槽位顺序模板**，同时写进工具 docstring（约束主 LLM 产参）和 `_TRANSLATE_SYSTEM`（约束翻译），两边用同一份：

```
[人数] → [角色tag] → [发型发色] → [服饰] → [饰品] → [表情] → [动作姿势] → [道具] → [场景背景] → [构图镜头] → [光线氛围]
```

配套规则：① 每个槽位给 1-3 个 tag，用户没提的槽位可留空但不得瞎编；② 只用 danbooru tag，不写叙述句；③ **质量词不输出**（工作流本体已承载，现状要求「质量词一个不漏」反而造成重复）；④ 角色名原样保留不翻译（角色 tag 由插件 LoRA 映射表自动挂载，翻译器瞎猜角色 tag 会造成干扰）。
- 影响：零风险、零配置；固定顺序本身对 CLIP 更友好；模板让「哪层丢了信息」肉眼可查。代价：docstring 变长（每轮多几十 token）；对纯风景类 prompt 模板略生硬（可在模板说明里豁免）。

**方案 S2（治 L2，小代码 + 外置词表）：tag 词表文件**
新增 `data/tag_presets.json`：按槽位分类的**推荐词表**（精选的、该 checkpoint 实测认识性好的 danbooru tag）+ **禁用/替换表**（实测出 artifacts 的词、常见误译 → 正确 tag）。翻译时把词表注入 system prompt（「优先从词表选词」）；替换表可做插件侧后处理替换（可选，二期）。
- 影响：tag 命中率直接提升——「模型没理解」很多时候是「给了个它不认识的词」；词表外置符合 D3 哲学（改表不改码），且词表可以靠日常翻车案例持续喂养。代价：词表需要人工维护和积累；system prompt 变长（翻译一次多几百 token，可接受）。

**方案 S3（治 L1，纯文案）：反压缩指令 + 用户原话透传**
- docstring 加一条：「用户明确提到的细节（服装/场景/动作/道具/人数等）必须全部体现在 prompt 里，不得概括省略」；
- 翻译调用附上**用户原话**作参考（「用户原话：…；LLM 提取的画面描述：…，请以两者并集还原画面，遗漏用户明确提到的细节视为失职」）——目前翻译器只能看到 LLM 转述后的词，L1 丢的细节永远救不回来。
- 影响：L1 损失的兜底网，成本极低。代价：用户原话可能含无关寒暄，需指令声明「只取画面相关信息」。

**方案 S4（治 L3，需汐小姐重新拍板，违反既有约束）：插入位置与权重**
两个子项，都触碰「追加式拼接、不动工作流原词」这条既定设计，**必须重新拍板才能实施**：
- S4a 插入位置：用户新词插到主正向词**开头**（或工作流里预留占位符 `{user}`）而非末尾，正面缓解 CLIP 尾部注意力衰减。这是对「内容不符」最硬核的一层修复，但改动拼接语义。
- S4b 权重语法：允许对 2-4 个关键 tag 加 `(tag:1.15~1.3)` 强调（ComfyUI 的 CLIPTextEncode 原生支持该语法）。不改拼接结构，只改翻译/产参的输出格式，温和一些；过重会出 artifacts，需限制区间。
- 附带诊断项（无需拍板）：拼接后总 token 超长时打 warning 日志（分块切断是常见隐性损失源）。

**方案 S5（治 L4，无代码）：重摇文化**
不符 ≠ 提示词错——SD 有采样随机性，同 prompt 重摇一次常常就对了。可在 docstring/衔接语层面引导「不满意可以喊重画一张」。无成本，属于预期管理。

#### 7) 追问：S1 与角色锁定基准词的重复堆叠分析（2026-10-24 第四轮，只分析未实施）

**问题**：基准词已含角色/发型发色类 tag 的工作流（如高清修复版），S1 槽位模板会不会导致重复堆叠？

**结论：S1 不会主动造成堆叠，且整体上减少了重复**：
- S1 没有改「基准词 + 追加」的拼接机制，只规范用户词内部的槽位取舍与顺序；规则①（没提的槽位跳过）反而减少了无中生有的 tag——**用户没提发型发色，用户词里就不会有发型发色 tag**，与基准词重复的前提不存在。
- 质量词/画风词：旧翻译指令要求「质量词一个不漏」，实际造成基准词 + 用户词双写 masterpiece 等；S1 规则③改为不主动补质量词，**消掉了这类重复**。
- 角色 tag：现有查重已覆盖——触发词追加前做全文包含检查（`trigger not in cur`，此时 cur=基准+用户词，main.py `_attach_role_lora`），已存在则不追加，**最多双写（基准+用户词各一次），不会三写**；LoRA 堆同文件命中时是更新权重而非追加条目。
- 人数 tag（1girl/solo 等）：基准词有的话会双写。影响轻微（重复 tag ≈ 轻微加权，提示词工程里常见且一般无害）。
- 真正的风险仍是**冲突而非重复**：用户明确提到的槽位与角色锁定基准词相反时（如黑发 vs 基准 `(pink hair:1.2)`），前置加权基准词压制尾部用户词——此为 S4 搁置的已知遗留项，S1 之前就存在。

**可选后续方案（若在意双写，未拍板）**：拼接时做 tag 级去重——用户词按逗号拆分，逐 tag 与基准词归一化比对（剥权重括号/`:x.x`/大小写后比对），已存在则跳过。确定性强、成本低；风险是误伤刻意重复强调（本流程来源为槽位模板普通 tag，刻意重复场景罕见）。靠 docstring 规则去重不可行——LLM 不知道工作流基准词里有什么。**待拍板，未实施。**

#### 8) 追问二：主动补全与角色锁定工作流的重复/冲突（2026-10-24 第五轮，主人纠正，只分析未实施）

**主人纠正（成立，推翻 7) 的乐观前提）**：实际使用中 bot 应当**主动补全**空白槽位（服饰/姿势/表情等）——大部分人只给简短描述让 BOT 自行发挥，不会发完整提示词。因此「用户没提的槽位 → 用户词里没有」不成立，与角色锁定基准词的重复前提**存在**。同时意味着现行规则①（「没提的槽位直接跳过，不要瞎编」）与期望行为**相反**，需要修订。

**对「用带昔涟 LoRA 的角色锁定工作流画昔涟」的精确对账**：
- 角色 tag（cyrene_(demiurge)）：**会双写**——用户词角色槽一次（规则④保留角色名，且 LoRA 匹配依赖它），基准词一次；触发词**不会三写**（追加前全文查重已覆盖）。
- 外貌词串（发型发色/瞳色/专属饰品等）：**会出现**——即使规则①禁止，强模型凭自身角色知识补全身份槽位是高概率行为。
- 且害处比重复更深：LLM 凭记忆写的外貌词可能与 LoRA 训练长相**不一致**（如发饰细节、瞳孔特征）——不是无害的重复加权，而是**与 LoRA 打架**，稀释角色还原度。

**修订方案（分层，待拍板）**：
- **L1 槽位规则改写（纯文案，治本方向）**：把槽位分两类——「自由槽」（人数/服饰/饰品中的非身份件/表情/动作姿势/道具/场景/构图/光线）：没提就**积极补全**，这正是 BOT 自行发挥的价值；「身份槽」（发型发色/瞳色/瞳孔特征/角色专属特征件）：**默认不写、留给基准词与 LoRA 承载**，仅当用户明确要求改变时才写（如"染成黑发""换发型"）。普适理由：任何挂 LoRA 的角色，其固有外貌由 LoRA 承载，prompt 里的外貌词至多冗余、往往冲突——此规则对角色锁定工作流与普通工作流同时成立。
- **L2 tag 级去重（小代码，兜底）**：即 7) 的 α 方案——拼接时逐 tag 与基准词归一化比对，拦住 L1 拦不住的精确重复（cyrene×2、pink hair×2、1girl×2）。注意：去重只治重复，**治不了冲突**（LLM 写 black hair 而基准是 pink hair，去重不会删——冲突靠 L1 的身份槽让位预防）。
- **L3 角色锁定标记（可选，暂不推荐）**：workflow_config 标记 + 翻译调用动态附加「勿输出外貌 tag」——只覆盖中文翻译路径，主 LLM 直出英文 tag 的路径覆盖不到，收益不全。

**建议组合**：L1 + L2。**待拍板后实施**（L1 改 docstring 与翻译指令两处文本；L2 改 `_submit` 拼接段）。

#### 9) 追问三：反作用与打架问题的方案修订（2026-10-24 第六轮，主人两次质疑成立，只分析未实施）

**质疑一（成立）：L1 二分法对无 LoRA 工作流有反作用**——若「身份槽默认不写」全局静态生效，快速出图版这类无角色承载的工作流画泛指人物时，prompt 无任何外貌来源 → 模型随机抽外观、bot 丧失造型能力。
**修正：让位规则按「画的是谁」区分，不按工作流区分**——
- 身份槽让位**仅对已注册 LoRA 角色生效**（外貌由 LoRA+触发词承载，写了反而打架）；
- 泛指人物/原创角色/未注册角色身份槽**照常积极补全**（此时 prompt 外貌词是唯一外观来源）；
- 判断主体是 LLM（分得清「昔涟」和「一个红发猫娘」），前提是它知道谁是注册角色 → **注册名单从 `character_lora_map.json` 动态生成注入工具描述**（加载时刷新，加角色改 JSON 即生效，延续 D3 哲学）；若框架 docstring 读取时机不支持动态注入，退化为「如昔涟、遐蝶等」示例式写法并标注档案同步义务。实施时需验证 `llm_tool` 对 docstring 的读取时机。

**质疑二（成立）：L2 治不了打架**——去重只删与基准词相同的 tag，LLM 写 `black hair` 而基准 `(pink hair:1.2)` 内容不同不会删。打架的正解是 L1' 让位（不写则无可打）；L2 明确定位为只治精确重复。

**补漏洞：显式变更的负向闭环**——用户明确要求改变注册角色固有外貌（黑发昔涟）时，仅正向写 `black hair` 压不过 LoRA → 规则要求**同时把原特征填进 negative 参数**（negative 追加机制现成），如 negative 补 `pink hair` 压制 LoRA 原长相。正向+负向双写形成闭环。

**修订后方案全貌**：L1' 槽位二分（按角色注册区分）+ 注册名单动态注入 + 显式变更负向闭环 + L2 去重（只治重复）。

### 议题 D6：受理状态回执与消息降噪（已实施，2026-10-24，v1.6.1 → v1.7.0）

**需求（主人提出）**：受理回执区分两种情况且走 LLM 吃人设——服务未启动 → 「收到生图请求，ComfyUI 正在启动」；已启动 → 「已收到生图请求 + 当前队列」。全程只在**收到任务**和**完成任务**时各发一条消息，等待/轮询等中间环节零噪音，仅报错时额外发消息。

**现状核对**：中间噪音原本就没有（拉起等待、轮询全程静默；插件直发消息仅存在于翻译失败/超时/异常三个报错路径，符合「仅报错额外发」）；完成消息 = 推图 + LLM 衔接语，已存在。缺的是**受理回执不区分状态**——旧返回值是固定中性句，不知道服务是否在启动、无队列信息。

**实施**：
- 新增 `_queue_brief()`（包 `cc.queue_status()`，running/pending 计数一句话；error/异常返回空串）。
- 工具入口在限流闸门**之前**探测 `cc.is_up()`（`asyncio.to_thread`，不阻塞事件循环；放在闸门前是为避免在 P4「检查→计数」之间引入 await 破坏原子性——回归断言已验证顺序）+ 服务就绪时取队列快照。
- 受理回执按探测结果三态：未启动（「正在后台自动拉起，可能需要一两分钟，就绪后自动入队」）/ 已就绪（队列快照「X 张生成中、Y 张排队等待」）/ 探测异常（中性「已受理，正在后台入队」）。回执文案末尾统一指令：LLM 用自己的话自然转述（吃人设）、不说模板台词、不预告完成时间。
- docstring【交付】补一句：中途无进度播报、只有出错才额外发消息。
- 服务实际拉起仍由后台 `_submit` 执行（P2 锁防双拉起不变）；探测与后台探活幂等重复无害。

**验证**：`py_compile`；`_queue_brief` 三形态单测（正常/错误标记/异常形态）；顺序断言（探测 < 限流检查 < 计数，且计数到 spawn 间无 await）；回执文本关键句断言。版本 1.7.0。
**备注**：本轮实施时发现主人手动改了 metadata.yaml 的 display_name（「昔涟の生图插件」），已保留。

### 议题 D4：问题池 P1–P8 批量整改方案（提案，2026-10-24，待审核）

> 原则：全部方案互不依赖，可逐项勾选；均不改变 D1/D2/D3 已定行为。
> 每项给出「改法 → 影响（收益/副作用/关联）→ 待拍板点」。

#### P1 历史注入并发覆盖（较高）

**改法**：插件实例加一把 `asyncio.Lock`；`_inject_image_sent_notice` 全程持锁，且**在锁内重新读取**最新 `conv.content` 再 append、立即写回——把竞态窗口从「出图全程几分钟」压缩到「读改写几毫秒」，并发注入同会话也因锁串行化。保留 try/except 兜底。

**影响**：
- 收益：出图期间用户继续聊天不再可能被旧快照整体覆盖（这是目前最可能实际丢数据的问题）；同会话连点两张图不再互相覆盖。
- 残余风险（如实说明）：与框架自身的对话写回之间仍存在毫秒级窗口（框架的 `_save_to_history` 也是读-改-写模式），但概率从「必然发生」降到「极难命中」，与框架自身设计水平一致。
- 副作用：无感知差异；锁仅覆盖注入瞬间，不影响出图耗时。
- 关联：β（注入提示含工作流）依赖本机制，本修复同时加固 β；仍使用 `conv_mgr.db` 内部 API，版本敏感性不变（try/except 已兜底为「注入失效但不报错」）。
- 已否决的更强方案：注入前探测会话活跃度、活跃则推迟合并——复杂度不成比例，不采用。

**待拍板点**：无（直接修）。备选「彻底删掉注入机制、只靠 docstring 防重复发图」不推荐——防重复发图/防重复跑图的效果会回退。

#### P2 冷启动双拉起竞态（中）

**改法**：模块级 `threading.Lock`（`_submit` 跑在线程池里，须用线程锁而非 asyncio 锁），包住「is_up → launch → wait_up」整段。第二个并发点单会等第一个拉起完成，再检查时 `is_up()` 已为真，直接走正常流程。

**影响**：
- 收益：杜绝双进程抢端口/抢 GPU；并发冷启动语义正确。
- 副作用：冷启动期间第二个请求会阻塞等待（最长 300s）后才报成功或失败——但相比现在的「第二实例崩溃留下一份困惑日志」，这是更正确的行为。
- 开销：ComfyUI 已在跑时锁内只做一次 `is_up()` 探测（秒级超时的 HTTP 探测），毫秒级，可忽略。

**待拍板点**：无。

#### P3 角色 LoRA 匹配时机（中）

**改法**：`_render_and_send` 保留翻译前的原始 prompt；`_submit` 增加可选参数 `role_match_text`（原始中文文本）；`_match_role_lora` 依次对「翻译后文本、原始文本」匹配，命中即用（触发词回填、权重照旧全部来自配置表）。翻译失败走现有降级路径不变。

**影响**：
- 收益：「昔涟」「德谬歌」等中文关键词真正生效，不再赌翻译器恰好输出 `cyrene` 等英文拼写；静默不挂 LoRA 的情况基本消除。
- 副作用：无；匹配是纯字符串包含判断，双文本匹配不会引入误挂（触发词/权重仍由配置表唯一决定）。
- 关联：无（与 D1–D3 正交）。

**待拍板点**：无。

#### P4 并发与频率限制（中）

**改法**：两层限制，阈值外置到 `data/workflow_config.json`（延续 D3 哲学：改文件热生效，不动代码）：
1. **全局并发上限** `max_concurrent`（建议默认 2）：插件维护活动任务计数，`comfyui_render` 入口超限直接返回「出图队列已满，请稍后再试」，不再堆后台任务；后台任务 `try/finally` 保证计数必然回落。
2. **每会话冷却** `cooldown_seconds`（建议默认 30）：`dict[umo → 上次启动时间]`，冷却中直接返回「刚才那张还在画，稍等一下哦～」。

**影响**：
- 收益：GPU 队列不被刷爆；同时收敛 P1（并发注入变少）与 P2（冷启动瞬时并发变少）的触发概率。
- 行为变化（用户可感知）：群友连点时，超额请求会**立刻**得到「队列已满/冷却中」的回复，而不是默默排队几十分钟后突然出图——这是预期中的体验改变。
- 副作用：计数器若在异常路径漏减会导致假满——用 try/finally 规避；冷却 dict 随会话数增长，量级可忽略。
- 关联：与 D1 noop 机制并存——限流文案是「正常业务回复」（LLM 会转述），与 noop 的「当无事发生」语义不同，docstring 里需各写一句避免 LLM 混淆。
- 备选：用 `asyncio.Semaphore` 排队而非拒绝——体验是「秒回但图很久才来」，用户无预期，不如显式拒绝；不采用。

**待拍板点**：① 两个默认值（建议 2 / 30s）是否认可；② 超限时对用户的话术由 LLM 转述（当前设计）还是插件固定文案。

### 议题 D3：工作流指定去硬编码（已定案并实施，2026-10-24）

#### 1) 背景与痛点（汐小姐提出）

工作流文件会被**改名、增删**，且这类调整很频繁；原来的固定别名表（`_WORKFLOW_ALIASES` 写死在代码里）、docstring 示例词、私聊默认常量全部随之失真——「这种事频繁地改动代码不合理」。

实证：实施时核对真实目录发现 `风堇` 工作流文件已不存在（旧别名表与 docstring 示例均已失真）；目录里另有 4 个点开头 `.bak_*.json` 备份残留（`ls *.json` 看不到、`os.listdir` 可见，会污染匹配）。

#### 2) 定案与实现

- **解析主路径 = 实时目录模糊匹配**：每次调用实时 `os.listdir` 工作流目录，按文件名子串匹配（大小写不敏感），排除点开头备份残留；命中多个返回候选清单，没命中返回实时候选清单（LLM 照单重新指定）——改名/增删零维护。
- **配置外置 `data/workflow_config.json`**（缺项用内置默认补齐，改文件即热生效，无需改代码）：
  - `workflow_dir`：工作流目录绝对路径
  - `fast_workflow`：群聊固定工作流关键词（默认「快速出图」；目录动态解析失败时退回内置 `_FAST_WF_PATH` 过渡兜底）
  - `private_default`：私聊粘性为空时的默认工作流关键词（默认「高清修复」，取代原 `_PRIVATE_DEFAULT_ALIAS` 常量）
  - `aliases`：可选「口语名 → 目标文件名子串」映射，仅当口语名不是任何文件名子串时才需要配，可空（原内置 7 条别名经核对全部是文件名子串，属冗余，故默认空表）
- **docstring 示例词去清单化**：不再列举具体工作流名（必过时），改为「以实时目录为准，找不到会返回候选清单」。
- 展示名 `_wf_display_name` 改为取文件名 stem（原别名反查表已删）。

### 议题 D2：私聊管理员工作流连续性（已定案并实施，2026-10-24）

#### 1) 背景与痛点

私聊管理员精细出图**保留**（D1 遗留决策点 1 定案），但实际使用暴露连续性缺陷：

- 快速出图版的定位是**群聊便捷**；私聊管理员出图时倾向使用更完善细致的工作流（礼服少女 / 高清修复 / 遐蝶调试…）。
- 现状是每次调用无状态：`workflow` 参数为空时**一律**回落快速出图版（main.py:118-119），上下文注入提示里也**不记录**本次用了哪个工作流（main.py:554-561）。
- 典型翻车场景：前两轮用「礼服少女」出了图 → 第三轮只说「换个服装/换个背景再出一张」（不重提工作流）→ LLM 省略 `workflow` 参数 → 被静默重置回快速出图版，画面质量/流程跳变。
- 「每一轮生图请求都完整指定工作流」不符合正常使用习惯。期望：**延续上一轮选择**，直到显式更换。

#### 2) 机理分析

- 工具本身无状态，LLM 侧能看到对话历史，但历史里没有机器可读的工作流记录（注入提示漏了这项），模型只能凭对话文本猜——省略参数是大概率事件，而省略 = 快速版。
- 群聊不受此影响（固定快速版是既定设计），问题域收敛在**私聊会话**，范围小、状态单一。
- 插件已有按会话定位的钥匙：`event.unified_msg_origin`（umo），以及现成的上下文注入机制（P1 所述机制，注意其并发风险）。

#### 3) 方案空间

**方案 α：插件侧会话粘性工作流（sticky workflow）** ✅ 主方向
插件内存维护 `dict[umo → 工作流]`（记录别名关键词 + 解析后的路径）。私聊解析顺序改为：
1. `workflow` 参数非空 → 按现逻辑解析，成功后**更新**粘性状态；
2. 参数为空但有粘性状态 → **沿用上次工作流**；
3. 参数为空且无粘性状态 → 私聊默认值（决策点 2）。

- 优点：确定性，零 LLM 负担，「不指定 = 延续」正好是用户直觉；群聊零影响；实现小（一个 dict + 三行解析顺序）。
- 代价：内存态重启丢失（回落默认值，可接受；如需持久化可仿 `character_lora_map.json` 落盘，建议先不做）；**失效语义需要定义**（决策点 3）；粘性状态跨对话重置残留（重置对话后仍沿用，见决策点 3 讨论）。
- 细节：别名命中时存「别名关键词」而非文件名，LLM 下次显式传参时用词一致；存路径也行但工具描述里的示例用词要对齐。

**方案 β：让 LLM 记住（docstring 约定 + 注入提示补工作流字段）** ✅ 辅助（与 α 叠加）
在 `_inject_image_sent_notice` 的注入文案里补上「本次工作流：XXX」，并在工具描述里写「用户未指定工作流时，沿用本会话上次使用的工作流（见历史中的系统图片交付提示）；用户要求更换时把新工作流关键词填进 workflow 参数」。
- 优点：无新状态；LLM 能**说出来**（"这张还是用礼服少女哦"）、也能主动显式传参更换；与 α 互为冗余（α 管「省略时用哪个」，β 管「LLM 知情与显式更换」）。
- 代价：概率性（模型可能忘）；加深对注入机制（P1）的依赖——**P1 修复时此功能跟着动**。

**方案 γ：只改私聊默认工作流（不引入粘性）**
把私聊空参数默认从快速版换成可配置的「私聊默认精细工作流」（如高清修复）。
- 优点：最小改动，缓解「掉回快速版」的突兀。
- 缺点：**不解决连续性**——礼服少女 → 高清修复照样跳变；只是把跳变目标换了个。仅当 α 被否决时作为退路。

**方案 δ：从对话历史反推（LLM 层，无插件状态）**
纯靠工具描述要求 LLM 每轮都显式回填 workflow 参数。
- 缺点：把确定性需求交给概率性记忆，模型漏填即翻车，与 α 重复且更弱。不采用，记录备查。

#### 4) 权衡对比

| 维度 | α 粘性状态 | β LLM记忆+注入 | γ 改默认 | δ 纯LLM回填 |
|---|---|---|---|---|
| 连续性确定性 | ★★★ | ★（概率） | ✗（只换跳变目标） | ★ |
| LLM 能否知情/主动更换 | ✗（插件黑盒） | ★★★ | ✗ | ★★ |
| 实现成本 | 低 | 极低 | 极低 | 极低 |
| 重启抗性 | 弱（回落默认） | 强（历史持久） | — | 强 |
| 新增风险 | 失效语义需定义 | 依赖 P1 机制 | 无 | 漏填即翻车 |
